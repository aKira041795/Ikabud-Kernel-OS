# Contract — P4.2a-r2 Modules & Extensions manager view

## Objective

Give Akira's admin an operator surface that lists suite members with their **real** installed/enabled
state and can install or enable them through the governed path.

P4.2a-r1 was correctly returned `BLOCKED / ARCHITECTURE_DECISION_REQUIRED`: `cms-akira-core` cannot
wrap `ModuleInstallService` because that service writes **kernel-owned control tables** (`kernel_tenants`,
install generations, activation state) and `kernel/Database/KernelPDO.php:88-100` explicitly blocks a
module from requesting kernel escalation. r1 was fully reverted and tenant 54 restored — no r1 code
remains.

**CHAIR DECISION CD-001** (authority: this contract, project contract `.ai/akira-master-plan.md`)
**Issue:** how a module-owned capability can reach kernel-owned install control tables.
**Options:** (1) narrow Kernel-owned escalation inside `ModuleInstallService` for its own control-table
writes only; (2) a new kernel trusted-service seam; (3) make `cms-akira-core` co-owner of tenancy
tables.
**Chosen:** **1**.
**Reason:** 3 is rejected outright — it would grant full CRUD over tenancy/install control tables and
weaken isolation; r1 already refused it correctly. 1 is the smallest change that preserves the
invariant and reuses the existing `KernelPDO::kernelEscalationEnter/Leave` primitive already used by
`kernel/App.php:216` and `kernel.provenance.list@1`. 2 is a larger new seam for no additional benefit.
**Owner intervention: not required.**

## Architectural constraints

- Kernel escalation must be **narrow and local**: it wraps only `ModuleInstallService`'s own writes to
  install control tables and activation state.
- Escalation **must not** cover module migration callbacks. A module's migrations must never execute
  with kernel privileges.
- Do **not** make `cms-akira-core` (or any module) a co-owner of kernel/tenancy control tables.
- Preserve existing authorization semantics. No role set, policy row, or guard is widened.
- `cms-akira-shell` remains contractually table-free (`owns_tables: []`, `reads_tables: []`); it reaches
  state only through capabilities. No SQL in the shell.
- Every new POST route is declared in `capabilities.routes` **and** its handler calls that same
  capability. A declared route whose handler does not call it fails closed and breaks.
- The capability is owned by a module (`cms-akira-core`); the kernel service provides the trusted write.
- `gui-settings` is a kernel companion and is **not** a precedent or a link target for any of this.
- MySQL 5.7 compatible: no CTEs, no window functions, `ENGINE=InnoDB`.

Binding prohibitions retained as text: no migration, DDL or schema change; no weakening of auth,
Authorisation, policy or security, and no widening of any role set or policy row; no making any module a
co-owner of kernel/tenancy control tables; no escalating module migration callbacks; no editing any
test, contract or baseline to obtain a pass; no SQL in `cms-akira-shell`; no deleting audit rows or
generation provenance; no widening scope to meet an acceptance criterion; no touching `gui-settings` or
linking to it.

1. `php -l` clean on every changed PHP file; `php _lint_disyl.php` clean on changed template dirs.
2. `modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` **still 116/0, exit 0**. The test is

3. `php ikabud module:validate cms-akira-core` and `... cms-akira-shell` pass.
4. The new page returns **HTTP 200** for the administrator on tenant 54 and lists modules whose state is
   **read from the real store** — paste the rendered rows and show they match
   `tenant_module_settings` (16 activation rows today).
5. **The toggle acts:** perform ONE enable/disable through the UI, read the resulting state back from

6. Migration callbacks do **not** run under kernel escalation — state how you verified this.
7. `storage/logs/error.log` unchanged by verification; `app.log` free of `disabled_caller` /
   `ModuleDB DENIED` authorization failures for the new paths.
8. Report residue: settings, policy rows, generations, audit rows created — what was cleaned and what
   was deliberately retained (audit rows and generation provenance must not be deleted).

## Risks

- **Escalation scope creep** — the escalation must not become a general "modules may write kernel
  tables" path. Bound it to this service's own control-table writes and say so in a comment.
- **Privilege leak into migrations** — the highest-risk failure mode; an escalated migration callback
  would let module code write kernel tables. Explicitly excluded and must be verified.
- **Mocking the store** — a view rendering a hardcoded or empty list reproduces the defect this
  programme has found seven times. Acceptance 4/5 exist to make that impossible.
- **Stale tenant state** — r1's experiment left recovery generations 14/15 and audit rows 2678/2679.
  These are retained deliberately as provenance; do not delete them, and do not assume they are inert
  without checking.
- **Live-tenant data loss** — tests must never bind to tenant 54
  (`requireNotLiveTenantDatabase()`); run the suite only against synthetic tenants.

## Failure protocol

Return `BLOCKED / ARCHITECTURE_DECISION_REQUIRED` with evidence and options if the narrow escalation
proves impossible or unsafe. Do not substitute a weaker-but-passing approach. Do not report a `SKIP` as
a pass. If a credential fails, stop and report rather than substituting weaker authentication evidence.
