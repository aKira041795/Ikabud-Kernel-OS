# Contract — P4.3 capability diff: what an extension would be granted

## Provenance

Chair-selected. It is the last chair-actionable row of the approved plan
`.ai/akira-master-plan.md:74` (`P4.3 extension trust / capability diff`), found by
`php tools/chair.php continue-check`, and the diff half of cycle **C6** in
`docs/architecture/akira-product-direction.md:96`:

> `| C6 | Extension trust: capability diff + Trust Center (P3) | install/update approval, revocation fallback |`

**The trust half is the director's and is OUT OF SCOPE.** P4.1 needs a trust basis (signed /
deployment-approved / operator-vetted) and is recorded as director-blocked. This slice builds the *report*
that an admission decision would be made from, and grants nothing.

## Objective

Answer the question an operator asks **before** admitting an extension:

> What authority would this install grant that the tenant does not already have, and **which of it writes**?

Deliver:

1. a **pure** diff function over two declaration maps,
2. a CLI report that runs it against a tenant's **active** install versus a candidate module set.

Nothing in this slice admits, approves, signs, revokes, or authorises anything. It reads manifests and
prints a difference.

## Architectural constraints

- **Pure first.** `Ikabud\Kernel\Workbench\Governance\CapabilityDiff::diff(array $before, array $after): array`
  is a function of its two arguments: no database, no session, no filesystem, no clock. Deterministic, and
  it leaves its inputs unchanged. Prove it.
- **The interface is fixed by a test the chair wrote and that you must not edit.**
  `tests/capability_diff_contract_test.php` is the acceptance and the specification. It requires
  `['added', 'removed', 'unchanged', 'widening']`, each a sorted list of ids:
  - `added` — present only in the candidate,
  - `removed` — present only in the active set, **named rather than ignored**,
  - `unchanged` — present in both,
  - `widening` — the subset of `added` that **writes**, sorted.
- **`widening` means "newly granted authority that writes", and nothing else.** A capability is a write
  when its declaration carries `requires_protocol: v2` or a non-empty `effects.invalidates`. An added
  *read* is NOT widening. A flag that fires on reads is a flag that gets ignored, and an ignored flag is
  worse than no flag — the same reasoning as `unprobed` in `plan`, and the same reasoning as the read/write
  split the census refuses to merge.
- **Reuse the existing module discovery and manifest reading.** `GovernanceCensus` and the module manager
  already resolve modules and read `module.json`. Do not write a second manifest parser.
- **Place it beside the census**, in `kernel/Workbench/Governance/`, which is where the route-authority
  diff already lives.
- **No capability, no route, no policy row.** This is a kernel CLI report. Adding a capability would be
  adding authority to answer a question about authority.
- The CLI is `php ikabud capability:diff --modules=<id,id,...>`. It diffs the union those modules declare
  against the tenant's **active** install and prints the four lists plus a `WIDENING: <n>` line naming the
  ids. **Exit 0** — it is a report, and a report that exits non-zero on a finding cannot be used in a pipe.
- MySQL 5.7 compatible. No schema change: this slice needs none, and adding one would require the director.
- State the population honestly: if a module id is unknown, say so rather than silently diffing a subset.

Binding prohibitions retained as text: no migration, DDL or schema change; no weakening of auth,
authorisation, policy or security; no widening of any role set or policy row; no editing any test,
contract or baseline to obtain a pass; no new capability in `kernel/`; no new route; no destructive or
irreversible operation; no widening scope to meet an acceptance criterion; do not read, copy or link
`gui-settings`.

**Explicitly out of scope, and named so it cannot drift in:** admission, approval, signature or trust
verification, revocation fallback, and anything that changes what the kernel permits. If the diff seems to
need one of those to be useful, that is a finding to report, not a licence to build it.

## Risks

- **Building the trust model by accident.** The single worst outcome is admission logic appearing in a slice
  whose whole justification is that it grants nothing. If you find yourself writing a signature check or an
  approval gate, stop and report.
- **A widening flag that fires on reads.** Then it is noise, and the operator stops reading it — the exact
  failure `plan`'s `unprobed` warning was built to avoid, where a guard gets ignored because it cries wolf.
- **A second manifest parser.** The census and module manager already parse manifests; two parsers will
  disagree, and the disagreement will look like a capability gap.
- **Silently diffing a subset.** An unknown module id that is skipped turns a complete report into a
  misleading one.
- **A report that exits non-zero.** Then it cannot be used in a pipe, and it will be `|| true`-ed into
  invisibility.
