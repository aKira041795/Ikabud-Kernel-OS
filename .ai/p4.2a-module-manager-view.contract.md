# Contract — P4.2a Modules & Extensions manager view

**Author:** chair · **Date:** 2026-09-14 · **Delegated to:** Codex Sol (`pi`)

## Objective

The director's complaint: **"no module/extension install view"**. Akira's admin has no way to see
which suite members are installed, or to install/enable one.

The machinery already exists and is governed. Only the **view** is missing — the same shape as P4.0,
where the customizer had a schema, a form, CSRF, audit and a capability, and was connected to nothing.

Deliver an operator surface in the Akira admin that lists suite members with their real installed /
enabled state and can install or enable them through the governed path.

## OWNER RULE — do not use gui-settings as a pattern

The director has ruled: **`gui-settings` is a `kernel_companion` and its scope is the kernel admin
surface only.** It is NOT a reference for any module's own settings/management UI. Do not read it as
precedent, do not copy its `settings_fields` shape, do not link to it. Akira does this on Akira's terms.

## Mandatory pre-flight — report file:line evidence BEFORE writing code

1. **Find the governed path.** Determine how a module is enabled/installed for a tenant today
   (`ModuleInstallService` call sites, the `ikabud tenant:module:install` CLI, any existing
   capability). Report exactly which capability, if any, already exists. If **none** exists, that is
   the main finding — say so plainly.
2. **Ownership decision.** A capability wrapping `ModuleInstallService` should be **owned by a module**
   (`cms-akira-core` is the likely owner), NOT added to `kernel/`. Report which you chose and why.
   **Adding a capability to `kernel/**` requires stopping and returning
   `BLOCKED / ARCHITECTURE_DECISION_REQUIRED`** — do not do it unilaterally.
3. **Shell table-free rule.** The shell MUST NOT read the database directly. It reaches state through
   capabilities. `shell_contract_test.php` must still pass **116/0** — **do not edit that test.**
4. **State source of truth.** Report where installed/enabled state actually lives and confirm by
   reading it (not by assuming from the manifest). Note that a module can be present on disk, declared
   in a profile, activated for the tenant, and loadable — four different things.

## Scope

**Allowed:**
- `modules/cms-akira/cms-akira-core/**` — the management capability + its policy seed
- `modules/cms-akira/cms-akira-shell/**` — the view, its route(s), the sidebar contribution
- `modules/cms-akira/cms-akira-*/module.json` — **additive** declarations only
- `modules/cms-akira/**/templates/**`, `modules/cms-akira/**/tests/**`
- One sidebar contribution entry

**Prohibited:**
- `kernel/**` and `src/**` (return BLOCKED instead — see pre-flight 2)
- Any migration, DDL, or schema change
- `storage/cms-themes/**`
- Editing any test, contract, or baseline to obtain a pass
- Weakening any authorization, role set, or policy
- Widening scope to meet an acceptance line

## Acceptance — evidence per line, no claims without evidence

1. `php -l` clean on every changed PHP file.
2. `php _lint_disyl.php <changed template dirs>` passes.
3. `modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` **still 116/0, exit 0**.
4. `php ikabud module:validate cms-akira-core` and `... cms-akira-shell` pass (use
   `HTTP_HOST=akiracms.test` if needed to avoid false dependency failures).
5. Every new POST route is declared in `capabilities.routes` **and** its handler calls that same
   capability — cite the handler line for each. (A route declared without a matching capability call
   fails closed and breaks; see the declaration test.)
6. **Live proof the view is REAL, not cosmetic:** on tenant 54 (`http://akiracms.test`, login
   `charlienacario884` / `aki123!#`), show the new page returning **200** and listing the actual
   modules with their **real** state. Paste the rendered rows. If the page renders an empty list or
   hardcoded rows, you have reproduced the defect — not fixed it.
7. **Live proof the toggle acts:** perform ONE enable or disable through the UI, show the resulting
   state change read back from the actual store, then **restore the original state** and show it
   restored. A claim without a state change is not evidence.
8. `storage/logs/error.log` unchanged by your verification; no product errors introduced. Check
   `app.log` for `capability.authz.decision` denials — a silently-denied nested capability is the
   documented failure mode (`disabled_caller`).
9. Report residue: any setting, policy row, generation, or audit row you created; what you cleaned up
   and what you deliberately left (audit rows must not be deleted).

## Failure protocol

- Return `BLOCKED / ARCHITECTURE_DECISION_REQUIRED` if the correct fix needs `kernel/**`, a migration,
  or a design decision not covered here — with evidence and options.
- Do NOT report a SKIP as a pass. If something could not be executed, say so plainly.
- If a credential fails, STOP and report — do not substitute weaker authentication evidence.
  (The password above is chair-verified; if it fails, something else is wrong.)

## Note for the implementer

This programme's recurring defect is **a declaration that does not control what it appears to
control** — seven instances so far, including the customizer that stored values nothing read.

A view that lists modules from a hardcoded array, or shows a state it never read, would be the eighth.
The acceptance criteria above exist specifically to make that impossible: the list must reflect the
real store, and a toggle must produce a real, verifiable state change.
