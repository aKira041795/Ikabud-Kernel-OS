Q1 DECISION: Federated with an explicit deny-wins precedence rule — tenant-local grant state is authoritative in each tenant's own database, plus one control-plane, deny-only containment overlay that can never grant.

WHY: The store has no tenant dimension at all: `migrations/016_capability_authorization_policies.sql` has no `tenant_id` column and the natural key is `(policy_version, capability_id, capability_version, provider)`. "Central with partitioning" therefore means rewriting that key and every existing row on a live MySQL 5.7 shared host. But pure per-tenant is also wrong, because the platform already holds authority it cannot surrender: `TenantResolver::tenantIsActive()` (`kernel/TenantResolver.php:243`) gates every host resolution on `kernel_tenants.status`, module catalog/access requests gate installation, and `provider_activation` is supplied by module activation. A provider with a security flaw must be stoppable in one write, not N. Crucially, the code says the *address* is not the bug: `CapabilityAuthorizationRegistry::db()` (`kernel/Capabilities/CapabilityAuthorizationRegistry.php:508`) is only a symptom of ambient resolution. `CapabilityBus::resolveTenantId()` (`kernel/Capabilities/CapabilityBus.php:671`) falls back to `app()->tenant()`/`kernel_request_context_get`, and `moduleRouteAuthorityDecision()` calls `app()->cap()->authorize()` (`src/helpers/module-manager.php:3026`). In CLI there is no `HTTP_HOST`, so `TenantResolver::doResolve()` falls through to `$this->default` (`kernel/TenantResolver.php:428-429`) and `DatabaseManager::db()` returns the base/kernel DB. If you "fix" this by only moving rows into tenant DBs, a cron/queue/bus caller gets `resolvePolicyVersion() === null` → `missing_active_policy_version` → denied, and `authorize()` denies first with `missing_tenant` (`CapabilityAuthorizationRegistry.php:71`). That converts a wrong-store bug into a denial-of-service aimed precisely at P3's `machine|service` actors.

CONSEQUENCES: Forces a single resolver contract, e.g. `AuthorityStore::forScope(AuthorityScope{tenantId, actor, declarationVersion})`, that is the only way any authority read/write obtains a PDO. Forbids constructing the registry with no DB (`CapabilityBus.php:330` `new CapabilityAuthorizationRegistry()`) and forbids `seedPolicy(app()->db())` in module helpers (`modules/cms-akira/cms-akira-*/helpers.php` — 8 modules). Forbids the control-plane overlay from ever holding `granted`; if it can, precedence becomes unwritable. Forces Workbench to pass an explicit tenant scope and to answer `unresolved_scope` (not "granted") when none exists.

FAILS IF: any deployment sets `APP_TENANT_DEFAULT` (single-tenant dev), which makes CLI and web resolve the same tenant and hides the defect entirely — the same code is fatal on multi-tenant production. Also fails if `kernel_tenant_db_connections` credentials are not reachable from a background control-plane process, because then the overlay cannot be enforced without an HTTP request.

COST: two stores plus a precedence fold forever; a new abstraction threaded through every call site; a migration on live tenants using the 017 idempotent-ALTER pattern. Hazard to verify first: the existing unique key spans `capability_id VARCHAR(191)` + `provider VARCHAR(191)` + `capability_version(32)` in utf8mb4 (~1656 bytes). If a tenant DB has `innodb_large_prefix=OFF` (index limit 767 bytes), the central-partitioning variant — and arguably migration 016 itself — is unshippable on that host until keys are shortened.

Q2 DECISION: Nothing may be centrally *issued*; exactly one class may be centrally *suspended/revoked* — any capability whose provider the platform has withdrawn or contained, including all `kernel.*` capabilities.

WHY: `CapabilityBus` already treats `kernel` as a non-tenant-scoped provider (`provider_activation => $providerId === 'kernel' || moduleIsActive(...)`), so its authority is structurally platform-level. Central issuance, by contrast, breaks the ADR's own sentence ("the tenant's authority store owns that decision") and, because there is no cross-database transaction on shared hosting, a provisioning fan-out that partially fails leaves some tenants granted and some not, invisibly. Central suspension is the concrete kill-switch the substrate needs for F4: without it, non-bypassability can only be proven one tenant at a time.

CONSEQUENCES: Central issuance is replaced by provisioning-time materialization — onboarding writes real `granted` rows into the tenant store inside the tenant's own transaction, and runtime never reads the control plane to *allow*. The overlay is checked before the tenant row and must yield a distinct reason (`central_suspension`) so provenance attributes it to the platform actor, not the tenant admin. Forbids a central `granted` row anywhere.

FAILS IF: a tenant admin can re-grant a centrally suspended capability (overlay not authoritative), or central suspension requires one write per tenant (then it is not central, and Q1's federated answer loses its justification).

COST: two denial reasons, two audit attributions, and a permanent, politically awkward reality: the platform operator has containment power over tenant sovereignty, so the contained write must be visible to the tenant or the sovereignty claim is theatre.

Q3 DECISION: Join declarations from versioned module contracts at runtime; the grant row stores an immutable declaration fingerprint pinned at grant time, never a mutable copy of roles/callers/protocol.

WHY: The current design is already a copy, and the copy is provably unsafe in both directions. `seedPolicy()` refreshes `caller_module`, `allowed_roles`, `provider_activation_required`, `requires_protocol` **only when granted** (`CapabilityAuthorizationRegistry.php:160-164`). So (a) a *granted* row silently widens when a deployment changes the declaration — a module upgrade can add authority with no operator decision, which is unacceptable on `daily-ledger`; and (b) a *suspended/revoked* row's declaration freezes forever, so a `requires_protocol v1→v2` security fix never reaches it and a later re-grant re-enforces a stale protocol. `tests/capability_policy_lifecycle_test.php:96-105` pins (b) as intended — that test conflates "cannot restore its grant" with "cannot rewrite its declaration". The cloning path is worse: `replaceActiveRowRoles()` (`CapabilityAuthorizationRegistry.php:305-360`) calls `seedPolicy()` first, which inserts the N+1 clone with `grant_state='granted'` and `is_active=1`, then re-transitions the non-granted rows; `resolvePolicyVersion()` selects `MAX(policy_version)`. If the caller did not supply the transaction the docblock demands ("The caller owns the surrounding transaction"), version N+1 goes live with **revocations resurrected as grants**. A fingerprint cannot drift into authority that way, and it is computable by Workbench from `module.json` without domain knowledge (F2/F3).

CONSEQUENCES: Forbids `allowed_roles`/`caller_module`/`requires_protocol` as authorization inputs on the row — they are derived at dispatch. `seedPolicy()` becomes an existence upsert only. `replaceActiveRowRoles()` must insert once with the final state instead of seed-then-re-transition. The fingerprint must be per row key `(capability_id, capability_version, provider)`, not per capability. Workbench and runtime must share one fingerprint function or F2 fails. Unavoidable prerequisite: declarations are *code, not data* — only 2 manifests declare `capabilities.policy` while 8 modules seed from `helpers.php`. "Join from contract" is unimplementable until those seeders become manifest declarations; that is the real first work item, and Q3 cannot be honest without it.

FAILS IF: two providers legitimately declare the same capability id with different role/caller sets; a per-capability fingerprint then wrongly denies. Keep it per row key.

COST: hashes are opaque in SQL — a human-readable `declaration_version` integer must accompany it. Every widening becomes an explicit operator re-grant, which will be the loudest complaint from anyone used to deploy-and-go.

Q4 DECISION: A code declaration change never mutates grant state. Narrowing applies immediately with no operator action; widening fails closed (grants become `declaration_drift`, requiring an audited re-grant); revoked grants stay terminal regardless of declaration change.

WHY: The safe direction of a temporary inconsistency is deny. Auto-narrowing only removes authority; auto-widening creates it. Therefore the projection must be refreshed in both cases (so runtime and Workbench agree) while the *effective decision* is the stricter of {pinned fingerprint, live declaration}. Revoked being terminal is what stops declaration drift from becoming a silent re-grant through the `replaceActiveRowRoles()` path above.

CONSEQUENCES: `seedPolicy()` must stop writing declaration terms on granted rows (kills the auto-widen at `:160-164`). `capability_policy_lifecycle_test.php` must be split into two assertions: grant_state stays revoked (keep), declaration projection is refreshed (invert). Recovery becomes read-derived — `effective = f(live declaration, pinned fingerprint, grant_state)` — so no reconciliation service and no repair job exists to get wrong; Workbench computes the same `f`. Requires adding `declaration_drift` to the 017 ENUM (`ALTER TABLE ... MODIFY COLUMN grant_state ENUM(...)`).

FAILS IF: the code declaration becomes observable at a different time than the pinned fingerprint's store. Today code ships on the app server while the tenant store is written by a later request or a manual CLI that resolves the wrong DB — so "stricter of the two" is not computable at the moment of the change. The fix is a monotonic `declaration_version` written into the tenant store by the same migration that changes the code; if that cannot be made monotonic on shared hosting, this answer is wrong and widening deploys must instead be blocked outright.

COST: a read-time comparison on the authorization path, and operators will see unexplained suspensions after some deploys — real support cost, and one that will tempt someone to disable the check.

Q5 DECISION: Revocation terminates the grant identity. Re-grant requires a new grant identity (new row/version) issued by an actor distinct from the revoker, with a mandatory reason referencing the revoked identity. Dual control (two distinct approvers) applies only to a declared `sensitive` class; `revoked → granted` is forbidden everywhere.

WHY: Provenance must read identically over a content revision and a ledger entry (C4/P1): "revoked by X at T; new grant by Y at T2, ref revoked-id" is readable, whereas a flipped flag destroys the question "was this ever revoked, and who undid it?" Distinct-actor — not two accounts — is the real SoD invariant, because a small Bluehost tenant often has exactly one human and dual control degenerates into the same person with two logins, i.e. the appearance of safety. The current code cannot even express the rule: `transitionGrantState()` (`CapabilityAuthorizationRegistry.php:198-230`) derives the actor from `app()->user()` and only asserts `id > 0`; there is no role check, no distinctness check, and in CLI `app()->user()` is null so revocation is *impossible* from a scheduled/service context today. That is why the rule belongs in the store, not the caller.

CONSEQUENCES: `transitionGrantState()` must reject `revoked → granted`. Actor identity becomes a first-class persisted column set — `{issuer, actor, tenant_id, issued_at, expires_at, revoke_of}` (P3's `Grant` shape pulled forward) — rather than derived at write time. The grant write and `kernel.audit.record@1` must share one PDO and one transaction; today the audit goes through `app()->cap()->call(...)` (`:265`) and resolves its own DB, so a registry built on a tenant PDO can commit the grant in one store and the audit in another. A `sensitive` class must be declared, not inferred, so containment re-grants get dual control and routine role changes do not.

FAILS IF: "distinct actor" cannot be evaluated because actor identity is not tenant-scoped. If the tenant is unresolvable (CLI/scheduled) and the implementation falls back to the ambient or kernel actor, this answer is wrong — the correct behaviour is to refuse.

COST: schema growth for the grant identity, a re-grant flow instead of a toggle, a deliberate refusal of the natural operator request ("just switch it back on"), and an audit comparison the enforcer must actually implement rather than assert.

THESIS: Authority scope must be an explicit, transportable argument — tenant + actor + declaration version — never an ambient property of the process. "Which database `app()->db()` happened to open" and "who `app()->user()` happens to be" are exactly the two things that differ between a web request and the cron/queue/bus contexts P3's delegated actors will run in. Every answer above is one answer: replace ambient resolution with a declared `AuthorityScope`; federation, the deny-only central overlay, fingerprint pinning, fail-closed-on-widen and new-grant-identity are all consequences of that single move.

DISAGREE: A "sovereignty" panellist will say pure per-tenant, no central store — that leaves the substrate with no cross-tenant kill-switch (F4 becomes unprovable at platform scope) and requires N writes to stop a bad provider. A "centralize it" panellist will say put the table in the control plane with a `tenant_id` — that puts a control-plane outage in the path of every tenant authorization, needs the natural key rewritten on a live MySQL 5.7 host, and still does not fix the defect, because `CapabilityBus::resolveTenantId()` and `moduleRouteAuthorityDecision()` fail before the store's address matters. Both will likely frame this as a storage migration; `CapabilityAuthorizationRegistry.php:508` shows the defect is `db()`, and the measured kernel-row/tenant-row split is a *symptom*: the workbench instrument still cannot see the runtime's decision at all.

UNRESOLVED: I cannot decide from the repo whether the control-plane deny overlay is operationally affordable, because I do not know (1) whether any scheduled/queue execution exists in this deployment (nothing in `kernel/` resolves a tenant without a host), and (2) whether `kernel_tenant_db_connections` credentials are usable from a background control-plane process rather than only from within a tenant request. Without that I still decide federated-deny-only: "no kill-switch" is worse than "N fan-out writes", and a deny-only overlay can degrade to fan-out writes later without changing the precedence rule. Separately unresolved: whether `capability_authorization_policies` is classified as a kernel-owned table for `KernelPDO` ownership purposes when it lives in a *tenant* DB — `withKernelTableAccess()` escalates for it unconditionally (`:469-490`), and if a future authority-store contract stops escalating, every module-originated policy read will be denied by `enforceModuleAccess()` instead.
