# Contract — P2.1 Navigation operator surface

**Author:** chair · **Date:** 2026-09-13 · **Delegated to:** Codex Sol (`pi`)

## Objective

Give `cms-akira-navigation` an operator surface. It currently exposes nine governed capabilities and
**zero routes**, is not consumed by the shell, and the only entry point is a health handler. Menus are
the single genuine orphan identified by both independent reviewers.

## Why the capability side needs no work

`cms-akira-navigation` already exposes (verified in `module.json`):

- reads: `akira.navigation.menus@1`, `akira.navigation.tree@1`, `akira.navigation.resolve@1`
- writes: `akira.navigation.menu.create@1` (idempotent, `requires_protocol: v2`, declares
  `effects.invalidates: [entity.list.navigation-menu]`), plus item create/update/delete and menu
  update/delete in the same family

Tables exist and are tenant-scoped: `cms_akira_menus`, `cms_akira_menu_items` (both carry `tenant_id`
inside composite unique keys — see ADR-002).

**This slice adds a surface, not a capability.** Do not design new capabilities.

## Copy the proven pattern — do not invent one

`cms-akira-theme` is the working precedent and must be mirrored:

| Element | Theme module (working) | Navigation (this slice) |
|---|---|---|
| Admin page route | `/cms-akira-theme` → `catThemeAdminPage` | `/cms-akira-navigation` → `akiraNavigationAdminPage` |
| Form POST routes | `/cms-akira-theme/activate`, `/cms-akira-theme/customize` | `/cms-akira-navigation/...` |
| Declared authority | `capabilities.routes` maps each POST to its capability | same |
| Sidebar entry | `admin_contributions` with `host: cms-akira-shell`, `location: sidebar` | same |
| Templates | module-owned `.disyl` | same |

## Mandatory pre-flight (do this BEFORE writing any route)

1. **Declaration test.** Declaring a route is safe only when its handler calls that same capability.
   This slice **adds new handlers**, so satisfy the test by construction: every new POST handler MUST
   call its capability through `app()->cap()->call(...)`, and only then may the route be declared.
   Do not declare a route whose handler does not call the capability, and do not skip a declaration
   for a handler that does. Report, per route, the handler line that performs the call.
2. **Policy pre-flight.** For every capability you intend to declare, confirm in the tenant DB that an
   **active** policy row exists whose `caller_module` permits the owning module and whose
   `allowed_roles` admits the actor. `caller_module` is the field that bites — a prior slice hit
   `disabled_caller` because the consuming module was not allowlisted.
3. **Role-set rule.** Any `admin_contributions` entry must declare the **same role set as the policy
   row it points at**, not a hand-written guess. The Theme Studio defect was exactly this: the
   contribution declared `["admin"]` while its policy admitted `admin,administrator,superadmin`, so a
   finished feature was invisible. Use `admin,administrator,superadmin` unless the policy row says
   otherwise, and say which row you checked.

## KNOWN DEFECT — fix as part of this slice (verified by the chair, not reported by you)

`modules/cms-akira/cms-akira-navigation/helpers.php:395` — `canNavigationActor()` refuses every role
that is not literally `admin`:

```php
if ((string) ($actor['role'] ?? '') !== 'admin') {
    throw new CanNavigationMutationException('Administrator role required.', 403);
}
```

The active policy rows for the navigation mutation capabilities admit
`admin,administrator,superadmin`. So the local gate is **narrower than the policy it sits behind**, and
its own error message contradicts it — it promises "Administrator role required" while refusing
`administrator`.

**This blocks the slice:** an authenticated `administrator` would pass policy authorization and then
be refused by the local gate, so the UI could not work for the only admin on the tenant.

**Required:** align the accepted role set with the active policy rows (`admin,administrator,superadmin`),
and keep the message truthful for whatever set you implement. This is the same correction already
applied to Theme Studio. Do not widen beyond the policy row's set.

3. `php _lint_disyl.php modules/cms-akira/cms-akira-navigation` passes on every new template.

6. The sidebar entry appears for an `administrator` — show the rendered `<nav>` destination list and
   its count before and after (it is currently 10; it should become 11).
7. Creating a menu through the UI produces exactly one audit row with a non-null actor, and a

## Constraints

- MySQL 5.7 compatible: no CTEs, no window functions, no `JSON_TABLE`.
- Tenant-scoped queries must filter `tenant_id` (ADR-002).
- Reads and writes go through the capability bus — never direct SQL from the shell.
- Follow `.github/instructions/php-module-conventions.instructions.md` and
  `disyl-template-conventions.instructions.md`.
- Failure must be visible: never silently degrade.

## Known environment traps — do not rediscover these

- `php -l` on a `.disyl` file is **meaningless** (parsed as inline HTML). Use `php _lint_disyl.php <dir>`.
- `php scripts/run-tests.php <file>` **ignores the path** and runs the whole suite, which also
  **unlinks `storage/modules.json`** and can poison the web APCu cache, 503-ing the live tenant. Run
  individual tests as `php tests/<file>.php` and capture `$?` via `> file 2>&1`.
- In CLI without a host, `app()->db()` resolves the **base** database, not the tenant. Use
  `dbForTenant(54)` for tenant state.
- PHPStan needs `-c phpstan.neon`; a bare file path analyses without the repo config.
