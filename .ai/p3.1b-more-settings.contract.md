# Contract — P3.1b Additional site settings

## Objective

Extend Akira's site-settings surface with **additional settings that each have a real render-time
consumer**. P3.1 proved the mechanism end-to-end with `public_posts_archive` (2 → 23 theme customizer
controls is unrelated; this is site behaviour). One setting is not a settings surface.

**The rule from P3.1 stands and is the whole point of this slice:** a setting whose only reader is the
settings page itself is a **defect, not a setting**. The theme customizer shipped as exactly that — a
schema, a form, CSRF, idempotency, audit and a governed capability connected to nothing — and it stayed
invisible for months.

**If a candidate setting cannot be given a real consumer, do NOT add it.** Report it as rejected instead.

## Architectural constraints

- Reuse the existing mechanism in `modules/cms-akira/cms-akira-core/helpers/settings.php`
  (`CAC_SITE_SETTING_*`, `cacSiteSettings*`, the `akira.site.settings.{get,public,update}@1`
  capabilities). Do not build a second settings store and do not add a new capability.
- Settings persist in `tenant_module_settings` under `cms-akira-core`. No new table, no new column.
- **Scope settings to module behaviour, NOT theme presentation.** Brand, colours, fonts and layout belong
  to `akira.theme.customize@1` and are out of scope.
- `cms-akira-shell` remains table-free. No SQL in shell code.
- Server-side, fail-closed validation for every new key: reject unknown keys, reject invalid values,
  never persist an empty value — fall back to the documented default.
- Every write idempotent and audited via `kernel.audit.record@1`; if the audit fails the write fails.
- MySQL 5.7 compatible: no CTEs, no window functions, `ENGINE=InnoDB`.

Binding prohibitions retained as text: no migration, DDL or schema change; no weakening of auth,
authorisation, policy or security; no widening of any role set or policy row; no editing any test,
contract or baseline to obtain a pass; no SQL in `cms-akira-shell`; no new capability in `kernel/`; no
theme-presentation settings; no setting without a named consumer; do not read, copy or link `gui-settings`.

**If a required path is not listed below, REPORT it rather than silently expanding scope.**

## Acceptance criteria

1. `php -l` clean on every changed PHP file; `php _lint_disyl.php` clean on changed template dirs.
2. `modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` **still 116/0, exit 0**. Do not edit
   that test.
3. `GET /cms-akira-shell/settings` returns **HTTP 200** and renders every setting **read from the store**
   — including `public_posts_archive`, which must keep working unchanged.
4. **Every new setting names its consumer with `file:line`**, and states what observable output changes
   when it changes. A setting read only by the settings page does not qualify.
5. **Proof the settings act:** for **each** new setting, change the value, show the **rendered public
   output changes** (paste before/after), then restore. A stored value is not evidence; changed output
   is. If any candidate cannot demonstrate this, say so and drop it rather than shipping it.
6. **Reject list:** state which candidate settings you considered and **rejected** for lack of a real
   consumer, and why. An honest rejection is a good outcome.
7. Invalid input refused fail-closed — demonstrate with a real request (unknown key AND invalid value).
8. Idempotency: two identical writes produce one stored change and one audit row.
9. `composer test` → report all three numbers (passed / failed / skipped). **Zero failures.**
10. `storage/logs/error.log` unchanged by verification.
11. Report residue: settings written, audit rows created; what was cleaned and what retained.

## Required tests

- `composer test` — full suite, zero failures (report all three numbers)
- `modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` (must stay 116/0)
- A test asserting each new key validates, rejects invalid values, and defaults safely when blank
- Live verification of acceptance 5 for each new setting

## Risks

- **The write-only defect.** The single most likely way to fail this slice. Acceptance 4, 5 and 6 exist to
  make it impossible.
- **Duplicating the theme customizer.** Brand/colour/font/layout already live under
  `akira.theme.customize@1`. Two sources of truth is worse than one missing feature.
- **Page cache masking.** Public rendering is cached; use a cache-busting query and confirm invalidation
  actually happened rather than assuming it.
- **Breaking `public_posts_archive`.** It works today and gates the whole public archive. A regression
  there fails the slice.
- **Live-tenant damage.** Tests must never bind to tenant 54.
