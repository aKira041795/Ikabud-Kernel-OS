GOVERNING PRINCIPLE IMPLEMENTED
  A verifier must be shown capable of failing before its pass counts as evidence.
  D1 refuses verifiers whose exit status is independent of state (a deny-list of
  constant-true shapes). D2 requires every evidence-required stage to declare a
  negative control that MUST exit non-zero; the runner executes it, and a control
  that exits 0 makes the stage UNPROVEN / NOT_FALSIFIABLE, never a pass.

WHAT REMAINS UNPROVEN (explicit, so this report is not read as full coverage)

1. Faithfulness of a negative control is not mechanically checked. The runner proves
   the declared control exits non-zero; it cannot prove the control exercises the SAME
   logic as `verify`. A manifest author could pair a cleverly vacuous (unlisted) verify
   with an unrelated always-failing control and still pass D2. The six shipped controls
   are constructed to exercise the verifier's own failure path (wrong-status compare,
   real whitespace error, real syntax error), and D1 catches the enumerated constant-true
   shapes, but "control exercises the verifier" is an authored property, not an enforced
   one. Closing it fully would require a mutation/derivation mechanism (out of scope for
   this last pre-freeze change).

2. D1 is a deny-list, not a decision procedure. Shapes outside the list (e.g.
   `bash -c 'exit 0'`, `[ -n "" ]` corner cases) are not refused by D1. They must still
   survive D1's sibling guard: if such a verify is combined with an honest control, the
   control is the only thing standing between it and a pass (see (1)).

3. Standalone jobs (`harpp job` / `track_job`) with a bare `verify` and no `evidence`
   field are unchanged and are NOT subject to D2. The contract scopes the fix to
   `evidence: required` workflow stages. Those job-level paths still accept `verify:
   "true"` and were deliberately left untouched to avoid weakening pre-existing tests
   (AC5). This is a known, disclosed gap, not a silent one.

4. `_stage_result_matches` still gates on `claim_status == RE_DERIVED` + `verify:PASSED`
   and was not changed to additionally require `negative_control_status == FALSIFIABLE`.
   The runner sets RE_DERIVED only after a falsifiable control for evidence-required
   stages, so the practical path is safe; a hand-forged structured result that omitted
   the control status would not be rejected by the identity check alone.
