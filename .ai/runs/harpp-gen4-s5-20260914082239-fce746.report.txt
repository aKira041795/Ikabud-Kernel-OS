## How a command binds, and why the commands below sit on their own lines

The harness extractor (`tools/ai-run.php:1343 parseCommandLine`) binds a command only when the
**whole line is the command** (optionally prefixed `$ ` or `> `; backticks allowed). A `COMMAND:`
label is prose to the extractor. So each claim below is written as a `COMMAND:` label line followed
by the exact command verbatim on its own line, so the extractor binds it and a reader can paste it
and see the same output. This is the adaptation already recorded for S6; it is a format adaptation,
not a relaxation.

Two kinds of evidence appear below:

- **Binding (executed by `verify`)**: the five pure harness suites and the two `py_compile` checks.
  These are the only commands this report needs the verifier to run, because they are pure and their
  claims can be re-derived without touching the live service.
- **Non-binding (shown verbatim, deliberately not executable)**: the sandboxed bridge-test
  invocations, `grep`, the manifest validator and the metrics command. They carry an environment
  assignment at the start of the line (`HARPP_NOTIFY=0 …`, `HARPP_CONFIG=…`) so the extractor does
  not classify them as commands. This is deliberate: the only allowlisted bridge-test command is the
  whole file `python3 tools/harpp-bridge/tests/test_harpp_wake.py`, which, run by the verifier
  without the sandbox, can reach the live service (finding F1). Declaring it re-derivable is exactly
  what the slice's absolute constraint forbids, so the sandboxed evidence is shown and not declared.

## Findings (reported, not fixed — fixing now would invalidate the verification)

**F1 — the bridge's own suite cannot be both green and safe under the contract's sandbox, and a
single test can reach the live service.** `HarppWakeTest.test_workflow_stops_after_max_repairs`
patches `harpp_client.send_message` but not `harpp_client.submit_decision`; when the workflow reaches
BLOCKED, `_notify_workflow` (`tools/harpp-bridge/harpp_wake.py:2101`) calls `harpp_notify`, which
calls the real `submit_decision`. Under the verifier's ambient environment (no `HARPP_NOTIFY`, no
sandbox `HARPP_CONFIG`), that issues a live "Workflow blocked:" decision. With the contract's
`HARPP_NOTIFY=0` the transport is neutralised (`submit_decision` returns `suppressed` before any
network call), but `_notify_workflow` returns early, so 19 notification tests then fail. Measured:
`HARPP_NOTIFY=0` full suite → `FAILED (failures=10, errors=9)`, exit 1, stub log 0 bytes.
Consequence: this run does not declare the full bridge-suite command as a re-derivable claim.

**F2 — the bridge's own model table still names the rejected `openai-codex/gpt-5.4`.**
`MODEL_ALIASES` (`harpp_wake.py:85`) and `MODEL_FALLBACK_ORDER` (`harpp_wake.py:100`) still contain
it, and `validate_workflow_manifest` accepts any model in either (`harpp_wake.py:2309`). D2 removed
it from the manifests, but an operator phrase ("5.4") or an exhaustion fallback can still resolve to
a dead lane. Bridge code is out of scope for this run: recorded, not edited.

**F3 — the mandated report format is not what the extractor parses.** The slice's literal
`COMMAND: <command>` line does not classify (`classifyCommand` is anchored at the start), so a
literal reading of revision 2 would extract no command and block as revision 1 did. The label line
plus a verbatim command line is the format that both reads correctly to a human and re-derives for
the verifier. Recorded so it is not rediscovered next slice.

## D1 — the evidence gate is authoritative (re-derived from the tree, not the commit message)

- `_stage_result_matches` (`harpp_wake.py:2395`) refuses the stage when `evidence == "none"` or when
  there is no `verify` (`:2409`), requires `claim_status == "RE_DERIVED"` (`:2411`), and requires
  `verify:PASSED` in the structured evidence (`:2413`). Pipeline (`verify:PASSED`, `marker:FOUND`)
  cannot advance a stage.
- `_report_job` computes `ok = verify_passed and claim_status == "RE_DERIVED"`
  (`harpp_wake.py:1651`); markers are informational (`:1633-1634`) and never enter `ok`.
- `_build_stage_result` (`:2364`) emits `marker:INFORMATIONAL:{FOUND|NOT_FOUND}` and
  `verify:{PASSED|FAILED}`, and carries `claim_status` (`:2389`).
- `validate_workflow_manifest` (`:2278`) rejects an unknown `evidence` value, requires `verify`
  unless `evidence == "none"`, and rejects `evidence: none` combined with a `verify` (`:2327-2334`).
- `_normalize_stage` (`:1219`) defaults `evidence` to `required` when a `verify` exists, else `None`
  (`:1230`).
