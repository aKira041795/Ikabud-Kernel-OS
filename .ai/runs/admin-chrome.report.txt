# Admin chrome slice — implementation report

## What was built

`akira.shell.admin_page@1` is exposed by `cms-akira-shell` as a **thin wrapper over `akiraShellPage()`**. `/cms-akira-seo` and `/cms-akira-navigation` render their body as a content fragment and hand it to that capability through the bus. One chrome implementation, three consumers. `akiraShellPage()` was not modified.

Files changed:

| File | Change |
|---|---|
| `modules/cms-akira/cms-akira-shell/module.json` | exposes `akira.shell.admin_page@1` (first-wins) |
| `modules/cms-akira/cms-akira-shell/helpers.php` | `cms_akira_shell_capability_handlers()` + `akiraShellCapAdminPage()` + `akiraShellSeedAdminPagePolicy()` |
| `modules/cms-akira/cms-akira-seo/module.json` | depends on the chrome cap; sidebar `active_key: "seo"` |
| `modules/cms-akira/cms-akira-seo/templates/admin.disyl` | fragment (no doctype/head/body/header/main/tailwind) |
| `modules/cms-akira/cms-akira-seo/handlers.php` | `akiraSeoRender()` wraps fragment via `akiraSeoShellChrome()` |
| `modules/cms-akira/cms-akira-navigation/module.json` | depends on the chrome cap; sidebar `active_key: "navigation"` |
| `modules/cms-akira/cms-akira-navigation/templates/admin.disyl` | fragment |
| `modules/cms-akira/cms-akira-navigation/handlers.php` | `akiraNavigationRender()` wraps fragment via `akiraNavigationShellChrome()` |
| `modules/cms-akira/cms-akira-shell/tests/admin_page_capability_test.php` | **new** gate (existing tests untouched) |

The capability handler is literally:

```php
return ['html' => akiraShellPage($title, $body, ['active' => $active])];
```

No navigation list is copied and no second page builder exists in either module.

## Decisions a reviewer will probe

- **Active keys.** The contract says the keys are `seo`/`navigation` and to confirm them. They did **not** exist: `kernelContributionNormalize()` leaves `active_key` empty and `akiraShellPage()` falls back to the contribution id (`cms-akira-seo.metadata`, `cms-akira-navigation.menus`). I confirmed this in code, then added the explicit `active_key` fields to the two sidebar contributions and passed `seo`/`navigation` — exactly the keys the contract names. Verified live: both sidebars highlight the current surface.
- **The title.** The shell renders the page title as its own `<h1>`. I removed the duplicate `<h1>` from each fragment (so each page has one `<h1>`), but the title text is preserved by being passed as the capability `title`; the description paragraph stays in the fragment. I checked this explicitly: rendered pages have `h1 count=1`, `SEO metadata` / `Navigation` titles, and the original descriptions.
- **If the capability call throws.** The wrapper catches `Throwable` (and an empty result) and returns a chrome-free document that still contains the fragment plus an alert and a link back to the dashboard. It never blanks the page and never recreates the old three-link header. The module's own admin gate already ran before render, so this is a degradation path, not an authorization bypass.
- **Policy.** Seeded via `cacActivePolicyVersion()` (no literal), provider `cms-akira-shell`, `caller_module = cms-akira-shell,cms-akira-seo,cms-akira-navigation`, `allowed_roles = admin,administrator,superadmin`. Confirmed live on tenant 54: an **active** row at `policy_version = 30` (the tenant's active version), `cms-akira-shell`/`cms-akira-seo`/`cms-akira-navigation` allowed, `cms-akira-theme` refused `disabled_caller`, `author` refused `role_not_allowed`. This is real live confirmation, not inference.
- **`cms-akira-theme` is out of scope.** Untouched. It remains the third offender with its own PHP-built chrome at `cms-akira-theme/helpers.php:1344`.
