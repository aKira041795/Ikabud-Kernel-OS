## S6 — make the loop usable: claims bind commands, blocked slices re-queue

Both repairs are implemented, tested and demonstrated. `ai-run.php` is the surface that binds
commands; `ai-loop.php` is untouched. S4's five claims now all bind to commands, and the live S4
slice has been re-queued through the recorded `retry` transition.

### D1 — which surface binds commands, and the two routes

The binding lives in `tools/ai-run.php` — the claim extractor (`extractClaims`, plus the new
`deriveTestCommand` / `testFileDerivationVerdict` / `parseInlineCommand`). The loop
(`tools/ai-loop.php`) is unchanged: it still only consumes claims and asks `verify` for statuses.
A claim records `subject.command_source`:

- **declared** — the evidence line carries the command: a whole line that is the command (optional
  `$ `/`> ` prefix, optional backticks), or one line that contains an allowlisted `php …` invocation
  together with its result. Shell chaining on an inline line is never bound.
- **derived** — a `TEST_RESULT` that names a test file but carries no command. Binding is exact-match
  only: an explicit `tests/<file>.php` token, or a bare name for which `tests/<name>.php` exists. The
  file must exist and pass the purity screen (no `bootstrap.php`, no `MODE_INTEGRATION`). The claim
  records `command_source: "derived"` and a `derivation` object.
- **null** — nothing bound; the claim stays `UNVERIFIED` and still blocks. The no-marker rule is not
  weakened.

Binding demonstration — one declared claim, one derived claim, and two refusals:

```
$ php tools/ai-run.php claims --id=bind-demo --runs-dir=/tmp/bind/runs --json
1 type=LINT_RESULT command="php -l tools/ai-run.php" source="declared" derivation=null
2 type=TEST_RESULT command="php tests/ai_contract_lint_test.php" source="derived" derivation={"attempted":true,"candidate":"tests/ai_contract_lint_test.php","refused":null}
3 type=TEST_RESULT command=null source=null derivation={"attempted":true,"candidate":"tests/no_such_test_xyz.php","refused":"test_file_missing"}
4 type=TEST_RESULT command=null source=null derivation={"attempted":true,"candidate":"tests/authority_scope_test.php","refused":"test_file_impure"}
```

Verification of the same run — derived binds and re-derives, missing/impure are refused and stay
UNVERIFIED:

```
$ php tools/ai-run.php verify --run=bind-demo --runs-dir=/tmp/bind/runs
  binding: rev=7e2492a03ef6421aa2fc4466b9d88eb2c7eb93ae dirty=yes
  [RE_DERIVED] LINT_RESULT  php -l tools/ai-run.php
      claimed {"syntax_ok":true,"exit_code":0} observed {"exit_code":0,"syntax_ok":true}
  [RE_DERIVED] TEST_RESULT  php tests/ai_contract_lint_test.php
      claimed {"passed":3,"total":3,"exit_code":0} observed {"exit_code":0,"passed":3,"total":3}

The existence and purity checks are the ones in `testFileDerivationVerdict`: `tests/no_such_test_xyz.php`
is absent, and `tests/authority_scope_test.php` exists but contains the integration/bootstrap markers,
so neither is bound.

### D2 — retry: the recorded way out of blocked

`php tools/ai-project.php retry --project=<id> --slice=<id> --reason="<text>"` records
`blocked → pending`, keeps the prior run id, and appends the reason to history. Live demonstration on
`harpp-gen4`:

```
$ php tools/ai-project.php retry --project=harpp-gen4 --slice=S4 --reason="S6 bound claim commands; re-dispatch S4 so its claims re-derive against the current tree (old run harpp-gen4-s4-20260914045055-cd664e preserved in history)"
SLICE S4 blocked -> pending (retry)
exit=0
```

The resulting `state.json` S4 record (written only by the tool): `state: pending`,
`run_id: harpp-gen4-s4-20260914045055-cd664e` (preserved), the retry reason, and history retaining the
block entry and its original reason:

```
"state": "pending",
"run_id": "harpp-gen4-s4-20260914045055-cd664e",
"reason": "S6 bound claim commands; re-dispatch S4 ...",
"history": [
  { "from": "pending", "to": "running", "run_id": "harpp-gen4-s4-20260914045055-cd664e", ... },
  { "from": "running", "to": "blocked", "run_id": "harpp-gen4-s4-20260914045055-cd664e", "reason": "claims were not all RE_DERIVED: UNVERIFIED,...", ... },
  { "from": "blocked", "to": "pending", "run_id": "harpp-gen4-s4-20260914045055-cd664e", "reason": "S6 bound claim commands; ...", ... }
]
```

Refusals, real output:

```
$ php tools/ai-project.php retry --project=harpp-gen4 --slice=S2 --reason=should-refuse
REFUSED: retry refused: S2 is done, not blocked
exit=3

$ php tools/ai-project.php retry --project=harpp-gen4 --slice=S4 --reason=
ERROR: malformed or repeated option --reason
exit=2
```

The empty/whitespace-reason refusal is also unit-tested (fixture test 10: `retry requires --reason`,
exit 2), and a retried slice is returned by `next` (fixture test 8: `NEXT S2`). On the live project
`next` is currently held by the running S6 dispatch, which is correct; once S6 closes, the re-queued S4
is next in table order.

### Acceptance 1 — ai-run.php is otherwise untouched (which surface binds)

The only `ai-run.php` change is in claim extraction/binding. The allowlist table (`COMMAND_ALLOWLIST`),
`classifyRun`, `commandCommitCheck` and `classifyCommand` are unmodified. The suite proves it:

Three regressions plus the sentinel (labels from that suite):

```

23. commit-check: silent -> exit 3, run named with its state
24. commit-check: failed -> exit 3, run named with its state

Test 29 plants a sentinel file via a chained command (`php -l tools/ai-run.php; touch <sentinel>`) and
asserts the sentinel does not exist: the command is refused with `command_not_allowlisted`, shown, and
never executed. The classification and commit-check cases are the same assertions that were green before
this slice.

### Acceptance 6 — the unblock proof on S4's existing run

`.ai/runs/` is forbidden, so I verified a byte-identical copy of the S4 record under `/tmp/s4verify/`
(same `--run` id; the report path resolves to the real report). The tracked S4 record is unchanged
(`git status` shows no modification under `.ai/runs/` other than this run's own new file). Result:

```
$ php tools/ai-run.php verify --run=harpp-gen4-s4-20260914045055-cd664e --runs-dir=/tmp/s4verify
ai_project_test           CONTRADICTED   claimed 6 tests,  observed 11
ai_loop_test              RE_DERIVED     observed 8 of 8
ai_run_test               CONTRADICTED   claimed 31 tests, observed 35
ai_autonomy_test          RE_DERIVED     observed 46 of 46
ai_project_metrics_test   RE_DERIVED     observed 16 of 16
summary: attempted=5 re-derived=3 contradicted=2 unverified=0
exit=3
```

All five claims now bind to commands (`command_source: derived`), which is the interface repair. Two
are CONTRADICTED because S6 legitimately added cases to those two suites, so their historical test
counts no longer match the current tree — the counts moved 6 → 11 and 31 → 35. That is honest evidence,
not a claim that S4 failed. The unblock is the `retry` above: re-dispatching S4 produces a fresh run
whose counts match the current tree. Nothing here required editing a forbidden path.
