## Objective

`token_version` revocation already exists, but it is only ever a **side effect**. Read
`cac_cap_akira_user_update_role_1` / `cac_cap_akira_user_set_active_1`
(`modules/cms-akira/cms-akira-core/helpers/governance.php:223,228`): both route into `cacUserMutate()`,
which ends by incrementing `token_version` (`:218`). So today **there is no way to revoke a user's
sessions without also changing their role or deactivating them.**

That is the missing primitive. Session revocation is an incident-response action: *"this account may be
compromised, sign it out everywhere, leave its access intact while we investigate."* Forcing an
administrator to deactivate a user to achieve it is the wrong lever, and it makes the action's
authority indistinguishable from a privilege change in the audit trail.

Deliver **session revocation as its own governed capability, with its own route, its own audit record,
and a visible effect on the users surface.**

## What to build

1. **Capability `akira.user.revoke_sessions@1`** exposed by `cms-akira-core`:
   - `capabilities.exposes` entry in `modules/cms-akira/cms-akira-core/module.json`, modelled on the
     neighbouring `akira.user.set_active@1` entry (`:109`) — same `requires_protocol: "v2"`, and an
     `effects.invalidates` block only if the neighbours carry one.
   - handler `cac_cap_akira_user_revoke_sessions_1` in
     `modules/cms-akira/cms-akira-core/helpers/governance.php`, delegating to a new
     `cacUserMutate('revoke_sessions', $payload)` branch, and registered in
     `cms_akira_core_capability_handlers()` (`modules/cms-akira/cms-akira-core/helpers/capabilities.php:18-20`).
   - **policy seed**: add `akira.user.revoke_sessions@1` to the loop in `cacSeedGovernancePolicies()`
     (`modules/cms-akira/cms-akira-core/helpers.php:298`). That loop already produces the exact tier —
     `caller_module: cms-akira-shell,cms-akira-core`, `allowed_roles: admin,administrator,superadmin`,
     `requires_protocol: v2`, `provider_activation_required: true`. **Do not hand-write a different tier.**

2. **Semantics — what revocation must and must not do.**
   - It **increments `token_version`** and leaves `role` and `is_active` **byte-identical**.
   - It is **audited** with the same envelope the other governance writes use.
   - It takes an **idempotency key**, like its neighbours.
   - It **refuses when the target is the acting user.** Message: `You cannot revoke your own sessions.`
     This is a deliberate decision, not an oversight — revoking your own sessions mid-request is a
     half-logout: the success banner would be flashed on a page the actor can no longer load, and if the
     target were the last administrator it would take the tenant's admin surface down with it. "Sign me
     out everywhere" is a different feature with a different UX and belongs on the account surface, not
     here. Mirror the existing self-guard at `governance.php:200` (`You cannot deactivate yourself.`).
   - It must **not** add a new "last administrator" guard. The existing guard protects against losing the
     last privileged ACCOUNT; revocation removes no account and no privilege, and the actor can sign back
     in immediately.

3. **Route and declaration** in `cms-akira-shell`:
   - `POST /cms-akira-shell/users/{id}/revoke` in `modules/cms-akira/cms-akira-shell/routes.php`.
   - handler `akiraShellUserRevokeSessions` in `modules/cms-akira/cms-akira-shell/handlers.php`,
     delegating like its neighbours do (`:1589,1594`) via `akiraShellUserMutation()`.
   - declaration in `modules/cms-akira/cms-akira-shell/module.json` under `capabilities.routes`, as a
     **map** keyed `"POST /cms-akira-shell/users/{id}/revoke" => "akira.user.revoke_sessions@1"`.

4. **Surface it on the users page** (`akiraShellUsers`, `handlers.php:1560`): add a `Revoke sessions`
   action beside the existing role and activate controls, and show each user's session generation
   (`token_version`) so the effect is observable rather than asserted. Keep the existing markup idiom and
   Tailwind classes; do not restyle the page.

## The safety invariant — the one thing that matters

**A declared write route whose capability has no active policy row 403s every operator**, because route
dispatch authority is fail-closed. Order of operations is therefore not optional:

**seed the policy → verify a row exists → only then declare the route.**

The role set must **EQUAL** what the handler chain already admits. `akiraShellAuthorizeAdmin()` is
`admin,administrator,superadmin`, and the seed loop above produces exactly that. Do not widen it
(granting access nobody has) and do not narrow it (403ing an operator who has access today). This
change alters *when* the authority decision is made, never *who* gets in.

If you cannot verify an active policy row for the new capability, **remove the route declaration** and
report — the fail-safe direction is today's behaviour.

## Architectural constraints

The capability bus is the only path to the database. `cms-akira-shell` must remain SQL-free: it reaches
data exclusively through `akiraShellCall()` / `akiraShellUserMutation()`. Do not add SQL to the shell.

The policy tier is not a design choice here — copy the existing governance tier exactly. A wider or
narrower tier is a privilege change and is out of scope.

Adding only a **POST** route is deliberate: the shell's declared GET read set must not change, because
`tests/read_authority_probe_test.php` asserts it exactly and has already been red once for exactly this
reason. Do not add, remove or reorder any GET route.

`modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` is the regression gate and **must pass
unmodified** — its route assertions use `isset()` on specific paths (`:141-142`), so an added route does
not break it. If it fails, that is a finding to report, not an assertion to adjust.

PHP 8.2-compatible syntax. No MySQL 8 features (production target is Bluehost/MySQL 5.7) — the
`@mysql57-compat` rules in `.github/copilot-instructions.md` apply. No new runtime dependency.

## Acceptance criteria

1. `akira.user.revoke_sessions@1` is exposed by `cms-akira-core`, has a handler in the capability
   handler map, and is seeded by `cacSeedGovernancePolicies()` at the same tier as
   `akira.user.set_active@1`.
2. Revocation increments `token_version` and leaves `role` and `is_active` unchanged — asserted by

3. Revoking the acting user's own sessions is refused with `You cannot revoke your own sessions.`
4. `POST /cms-akira-shell/users/{id}/revoke` is declared in the shell manifest and resolves to the new

   `cms-akira-core` and whose `allowed_roles` is `admin,administrator,superadmin`.
6. `php modules/cms-akira/cms-akira-core/tests/user_revoke_sessions_test.php` exits 0.
7. `php modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` passes **unmodified**.
8. `php -l` reports no syntax errors on every changed PHP file.
9. The governance census reports the new write route as **declared**, and the shell's

## Risks

- **Fail-closed dispatch.** Declaring the route before the policy row exists returns 403 to every
  operator. If you are unsure the row landed, remove the declaration and report.
- **A skip that looks like a pass.** If the guard skips the new test, its assertions never ran; report
  that rather than presenting a green exit code as coverage.
- **Idempotency double-charge.** Replaying the same `idempotency_key` must not increment
  `token_version` twice. Assert it.
- **Self-revocation via a stale session.** The refusal must be evaluated against the acting identity, not
  a hidden form field. Do not trust a client-supplied actor id.
