# Contract — P1.3 / B1 Tenant activation must govern capability dispatch

## Objective

Close the gap where **tenant module activation declares an entitlement that capability dispatch
ignores**. A module can be marked `_module_enabled = false` / unactivated for a tenant, yet its
capabilities still dispatch, because nothing in the bus consults activation state.

This is the ninth instance of the programme's recurring defect: *a declaration that does not control what
it appears to control.*

**B1 (chair, decided): enforce — but dependency closure FIRST.** Enforcement applied without a correct
closure would refuse capabilities the live tenant currently depends on and take tenant 54 down. Order is
mandatory, not a preference.

## Architectural constraints

- **Phase 1 is a report, not a change.** Before any enforcement code is written, measure and report the
  dependency closure for tenant 54 and state exactly which capabilities are reachable, from which
  activated modules, and what the closure computation is based on. Evidence or it did not happen.
- **Enforcement must be fail-safe, not fail-catastrophic.** A capability must never be refused because
  activation state could not be *resolved*. Unresolvable state means **allow** and log; resolved-and-
  inactive means refuse. Getting this backwards takes the site down.
- Enforcement must not apply to the kernel host or to public (anonymous) render paths unless you prove
  those paths already resolve a tenant. Public pages must stay 200.
- Do not weaken authentication, authorisation, policy, or security anywhere. This slice **adds** a
  refusal, it never removes one.
- Do not delete or edit an existing policy row. Activation gating is a **separate** check from policy
  authorisation; keep them distinguishable in logs so a future reader can tell which one refused.
- `cms-akira-shell` remains table-free; no SQL in the shell.
- Every refusal must be observable in `app.log` with a distinguishable reason
  (e.g. `module_not_activated` vs the existing `role_not_allowed` / `disabled_caller`).
- MySQL 5.7 compatible: no CTEs, no window functions, `ENGINE=InnoDB`.

Binding prohibitions retained as text: no migration, DDL or schema change; no weakening of auth,
authorisation, policy or security; no widening of any role set or policy row; no deleting policy rows;
no editing any test, contract or baseline to obtain a pass; no SQL in `cms-akira-shell`; no disabling a
working capability to make a check pass; do not read, copy or link `gui-settings`.

## Acceptance criteria

**Phase 1 — closure report (BEFORE any enforcement code)**

1. Report the dependency closure for tenant 54: which modules are activated, which capabilities each
   provides, and which capabilities the live surfaces actually call. Cite how you obtained each fact
   (`file:line`, a query, or a live request).
2. State the closure rule you will implement and the exact cases it treats as allow vs refuse.
3. If the closure cannot be computed from available data, **STOP and return
   `BLOCKED / ARCHITECTURE_DECISION_REQUIRED`** with the evidence. Do not implement enforcement on an
   unproven closure.

**Phase 2 — enforcement (only if Phase 1 is sound)**

4. `php -l` clean on every changed PHP file; `php _lint_disyl.php` clean on changed template dirs.
5. **The live tenant must be completely intact.** Enumerate and paste: `/`, `/posts`,
   `/posts/welcome-to-akira`, `/login` (anonymous, all must be 200) and every shell surface you can
   reach — `/cms-akira-shell`, `/posts` admin, `/categories`, `/content-types`, `/media`, `/permissions`,
   `/authority`, `/provenance`, `/modules`, `/users`, `/workflow`, `/search`, `/settings`, `/backups`
   (authenticated, all must be 200). **A single regression here fails the slice.**
6. `composer test` → report the full three numbers (passed / failed / skipped). **Zero failures.** Run it
   — do not reason about it.
7. Shell contract still **116/0**.
8. **Prove the enforcement works:** show a capability being refused because its module is not activated
   for a tenant, with the `app.log` reason string. Use a **synthetic tenant** for this — do not
   deactivate a module on tenant 54 to prove it.
9. **Prove fail-safe behaviour:** show that unresolvable activation state **allows** rather than refuses.
10. Confirm you did not delete or modify any existing policy row — show the row count before and after.
11. `storage/logs/error.log` unchanged by verification.
12. Report residue and what you retained.

## Risks

- **Taking the tenant down.** The dominant risk. Closure computed wrongly refuses capabilities the live
  site needs. Acceptance 5 is deliberately exhaustive for this reason.
- **Fail-open/fail-closed inversion.** Unresolvable state must allow. Refusing on an unresolved lookup
  turns a transient read failure into a site outage.
- **Conflating gates.** Activation is not authorisation. Log them distinctly; never let an activation
  refusal masquerade as a policy refusal or vice versa.
- **Scope creep into policy.** Do not "clean up" policy rows while you are in there.
- **Test tampering.** If a test fails because enforcement is wrong, fix the enforcement — never the test.

## Failure protocol

`BLOCKED / ARCHITECTURE_DECISION_REQUIRED` is the **correct** outcome if the closure cannot be proven or
if enforcement cannot be made fail-safe. Returning it is success, not failure. What is not acceptable is
shipping enforcement on an unproven closure or regressing a single live route.
