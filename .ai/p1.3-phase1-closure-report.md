- explicit activation → `readTenantModuleSettingsForTenant()` (`src/helpers/module-manager.php:1417`).
- always-active closure → `moduleRegistryAlwaysActiveForTenant(54)` (`src/helpers/module-registry.php:481`).

Why `workflow`/`search` are in the closure without an activation row:

- `cms-akira-shell/module.json` → `"depends": ["cms-akira-core", "cms-akira-workflow"]` (module-level).
- `cms-akira-shell/module.json` → `capabilities.depends` includes `akira.search.query@1`,
  `akira.search.rebuild@1`, which only `cms-akira-search` exposes.
- `moduleRegistryAlwaysActiveForTenant()` walks both module `depends` and capability
  `depends → exposes` (`src/helpers/module-registry.php:542-580`).

Combined operational set for tenant 54 = **10 modules**:
`core, shell, theme, media, navigation, seo, editor, builder` (explicit) ∪
`shell, core, workflow, search, media, theme, seo` (closure).

## 5. What HEAD already does, and the real residual gap

Contrary to the finding text, the bus **does** consult activation today:

- `CapabilityBus::applyPolicy()` (`kernel/Capabilities/CapabilityBus.php:508-522`) skips any
  provider with `!moduleIsActive($pid)`.
- `provider_activation` is also passed to the policy registry in `authorize()`
  (`:371`) and `applyAuthorizationRegistry()` (`:623`); the registry refuses it as
  `disabled_provider` (`CapabilityAuthorizationRegistry.php:...`).

So the defect is **not** a total absence of enforcement. The residual, demonstrable defects are:

1. **Not fail-safe.** `moduleIsActive()` returns `bool`; a lookup that cannot be resolved
   (tenant DB unavailable, unknown tenant) collapses to `false` → refusal. The contract requires
   *unresolved → allow, log*.
2. **Implicit tenant.** The gate calls `moduleIsActive($pid)` with **no tenant**, relying on ambient
   request state, while the authorization layer resolves an explicit tenant. They can disagree.
3. **Conflated reason.** When the gate empties the provider list, `call()` logs
   `caller_policy` and throws `CapabilityNotFoundException` — indistinguishable from a real caller
   policy denial. The contract requires a distinct `module_not_activated`.
4. **No test** asserting active→allow / inactive→refuse / unresolved→allow.

## 6. Closure rule Phase 2 will implement

For a provider module `M` and a resolved tenant `T` (kernel provider always active):

| Case | State | Dispatch |
|---|---|---|
| `M === 'kernel'` | active | **allow** |
| `M` has `_module_enabled: true` for `T` | active | **allow** |
| `M` is in the entry-module closure of `T` | active | **allow** |
| Tenant `T` resolves, activation store reads, `M` not above | inactive | **refuse** `module_not_activated` |
| Multi-tenant mode and no tenant can be resolved | unresolved | **allow**, log `module_activation_unresolved` |
| Tenant DB / activation store unavailable | unresolved | **allow**, log |
| `M` not a discovered module (unknown provider) | unresolved | **allow**, log |
| Any exception while resolving | unresolved | **allow**, log |

Order: **closure is already present and proven (§3), so enforcement may land**. The gate runs as a
check *separate* from policy authorization; a resolved-inactive module is refused before the policy
registry runs, and the log reason is `module_not_activated` (never `role_not_allowed` /
`disabled_caller`). A policy row is never edited or deleted.
