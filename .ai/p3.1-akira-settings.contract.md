# Contract — P3.1 Akira site settings surface

## Objective

Give CMS Akira a settings surface for **site behaviour**, on Akira's own terms. Every setting must have
a **named render-time consumer** — a setting that is stored but read by nothing is a defect, not a
setting. This slice exists because the theme customizer was exactly that: a schema, a form, CSRF,
idempotency, audit and a governed capability — connected to nothing.

`gui-settings` is a kernel companion and is **not** a pattern, precedent, or link target here. Do not
read it, copy it, or reference it.

## Architectural constraints

- Settings persist in the tenant's module settings under the owning module (`cms-akira-core`). No new
  table, no new column.
- `cms-akira-shell` remains contractually table-free (`owns_tables: []`, `reads_tables: []`). It reads
  and writes only through capabilities. No SQL in the shell.
- The capability is owned by `cms-akira-core`. Do not add anything to `kernel/`.
- Every new POST route is declared in `capabilities.routes` **and** its handler calls that same
  capability. A declared route whose handler does not call it fails closed and breaks.
- **Every setting must name its consumer** in the code and in the report, with file:line. A setting with
  no consumer is not added.
- Settings covered by the theme customizer (brand, colours, fonts, layout) are **out of scope** — those
  belong to `akira.theme.customize@1` and are already delivered. Do not duplicate them.
- Scope settings to behaviour the **module** controls, not presentation the theme controls.
- Validation is server-side and fail-closed: reject unknown keys and invalid values rather than storing
  them. Blank must fall back to the documented default, never persist an empty value.
- Writes are idempotent and audited via `kernel.audit.record@1`; if the audit fails the write fails.
- MySQL 5.7 compatible: no CTEs, no window functions, `ENGINE=InnoDB`.

Binding prohibitions retained as text: no migration, DDL or schema change; no weakening of auth,
authorisation, policy or security; no widening of any role set or policy row; no editing any test,
contract or baseline to obtain a pass; no SQL in `cms-akira-shell`; no widening scope to meet an
acceptance criterion; no new capability in `kernel/`.

## Acceptance criteria

1. `php -l` clean on every changed PHP file; `php _lint_disyl.php` clean on changed template dirs.
2. `modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` **still 116/0, exit 0**. Do not edit
   that test.
3. `php ikabud module:validate cms-akira-core` and `... cms-akira-shell` pass.
4. `GET /cms-akira-shell/settings` returns **HTTP 200** for the administrator on tenant 54 and renders
   the current values **read from the store** — paste the rendered field values alongside the stored
   values and show they agree.
5. **Every setting names a consumer.** List each setting with the file:line that reads it, and state
   what observable output changes when it changes. A setting whose only reader is the settings page
   itself does not satisfy this.
6. **Proof the settings act:** for ONE setting with a public-facing consumer, change the value, show the
   **rendered public output changes** (paste before/after), then restore and show it restored. A stored
   value is not evidence; changed output is. If no setting can demonstrate this, say so plainly and
   return the slice as not meeting its objective rather than shipping a write-only surface.
7. Idempotency: two identical writes produce one stored change and one audit row.
8. Invalid input is refused fail-closed with a clear message — demonstrate with a real request.
9. `storage/logs/error.log` unchanged; no `disabled_caller` authorization failures in `app.log`.
10. Report residue: settings written, audit rows created; what was cleaned and what was retained.

## Risks

- **The write-only defect.** A settings page that stores values nothing reads is the defect this
  programme has found eight times, most recently in the theme customizer. Acceptance 5 and 6 exist to
  make it impossible.
- **Duplicating the theme customizer.** Brand/colour/font/layout settings already exist under
  `akira.theme.customize@1`. Re-implementing them here would create two sources of truth.
- **Cache masking.** Public rendering is page-cached; a change may not appear until invalidation. Use a
  cache-busting query when verifying and confirm the invalidation actually happened.
- **Live-tenant damage.** Tests must never bind to tenant 54. Use a synthetic tenant for the suite.
- **Scope creep** into a general "everything is a setting" surface.

## Failure protocol
