# Contract — P3.2 Workflow / approvals console

## Objective

Give CMS Akira an operator surface for **workflow state**: what is awaiting action, and the ability to
advance it through the governed transition path.

The machinery already exists and is unused by any surface: `cms-akira-workflow` exposes
`akira.workflow.runs@1`, `akira.workflow.evaluate@1` and `akira.workflow.transition@1`, but the module
declares **zero** `admin_contributions` — so there is no operator view for any of it. This is the same
shape as the theme customizer and the module manager: capability present, surface absent.

## Architectural constraints

- The surface reads real workflow state through `akira.workflow.runs@1` and mutates only through
  `akira.workflow.transition@1`. It must not invent a parallel state model.
- `cms-akira-shell` remains contractually table-free (`owns_tables: []`, `reads_tables: []`). No SQL in
  the shell. All state and mutations traverse capabilities.
- Do not add capabilities to `kernel/`. If a genuinely new capability is required, it belongs to the
  owning module (`cms-akira-workflow`).
- **Declaration test:** every new POST route is declared in `capabilities.routes` **and** its handler
  calls that same capability. A declared route whose handler does not call it fails closed and breaks.
- **Policy pre-flight:** for each capability the surface declares or newly consumes, confirm in the
  tenant DB that an **active** policy row exists whose `caller_module` permits the calling module and
  whose `allowed_roles` admits `administrator`. Report the row. A missing caller allowlist is the known
  silent-degradation failure (`disabled_caller`, widget renders nothing).
- **Role-set rule:** any contribution must declare the **same role set as the policy row it points at**.
  Do not hand-write a guess — three features have already been hidden by exactly this mistake.
- **Local-gate check:** if the module has a `*Actor()` / `can*()` guard, compare its accepted role set
  with the policy row and align it. Three guards so far were narrower than the policy behind them.
- An **empty** list is a legitimate outcome and must be rendered as an explicit empty state. An empty
  list is never evidence that the feature works — say plainly what you observed.
- MySQL 5.7 compatible: no CTEs, no window functions, `ENGINE=InnoDB`.

Binding prohibitions retained as text: no migration, DDL or schema change; no weakening of auth,
authorisation, policy or security; no widening of any role set or policy row; no editing any test,
contract or baseline to obtain a pass; no SQL in `cms-akira-shell`; no new capability in `kernel/`;
no widening scope to meet an acceptance criterion; do not read, copy or link `gui-settings`.

## Acceptance criteria

1. `php -l` clean on every changed PHP file; `php _lint_disyl.php` clean on changed template dirs.
2. `modules/cms-akira/cms-akira-shell/tests/shell_contract_test.php` **still 116/0, exit 0**. Do not edit
   that test.
3. `php ikabud module:validate cms-akira-workflow` and `... cms-akira-shell` pass.
4. The console returns **HTTP 200** for the administrator on tenant 54 and renders workflow state **read
   from the real store** via `akira.workflow.runs@1`. Paste the rendered rows.
5. **State the population honestly.** Report how many workflow runs exist for tenant 54. If there are
   none, say so and show the empty state — do **not** manufacture rows to make the page look populated.
   If the list is empty, additionally demonstrate the read path against a synthetic tenant or a
   temporary governed record that you clean up, and say which you did.
6. **The transition acts.** Perform ONE real transition through the console, show the resulting state
   read back from the store, then restore it or state clearly that it is not restorable and why.
7. Idempotency: a repeated transition with the same idempotency key does not double-apply.
8. Unauthorized role is refused fail-closed — demonstrate with a real request.
9. `storage/logs/error.log` unchanged; no `disabled_caller` authorization failures for the new paths.
10. Report residue: rows, audit entries, policy rows created; what was cleaned and what was retained.

## Risks

- **Fabricated state.** A console rendering a hardcoded or seeded-looking list would be the defect this
  programme has found eight times. Acceptance 4 and 5 exist to prevent it.
- **Silent capability denial.** A nested capability denied for `disabled_caller` renders nothing and
  looks like "no data". Check `app.log` for `capability.authz.decision` with `allowed:false`.
- **Empty list misread as success.** An empty approvals queue is plausible and is not proof of function.
- **Duplicating workflow semantics.** Reuse `akira.workflow.transition@1`; do not re-implement the state
  machine in the shell.
- **Live-tenant damage.** Tests must never bind to tenant 54; use a synthetic tenant for the suite.
