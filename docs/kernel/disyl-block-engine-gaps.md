# DiSyL block-engine readiness for T4

Date assessed: 2026-09-10. All observations below came from executable renders, not source inspection alone. The focused proof is `tests/disyl_block_engine_readiness_test.php`; it loads renderer paths from the real Akira Ark `block-definitions.json` and copies the real block templates unchanged into an isolated template root.

| Capability | Needed by T4 | Current status | Empirical evidence (template and observed result) | Decision |
|---|---|---|---|---|
| Dynamic per-block template resolution | Select `renderer.template` for every section without an ID ladder | **supported** | Proof template: `{foreach sections as section}{include section.template props=section.props}{/foreach}`. With `section.template=blocks/hero.disyl`, both interpreted and compiled renders contained `<h1>&lt;Ready&gt;</h1>`; with `blocks/card-grid.disyl`, both contained `<h2>Cards</h2>`. Before this slice, the same unquoted include target remained unprocessed in the interpreted path and v4 parsed an empty include path. | **fix-at-engine-root**, closed by dynamic include expressions |
| Whole context object passing | Expose a block's complete props map as `props` | **supported** | The same proof passes `props=section.props` (an array, not expanded pairs). The unchanged real hero template resolved `{props.title}` and the unchanged card-grid iterated `{foreach props.items as item}`. Observed hero title: `<h1>&lt;Ready&gt;</h1>`. | **fix-at-engine-root**, closed through include parameter expression evaluation in both paths |
| Loops and conditionals over block arrays | Traverse sections/items and optional values | **supported** | Proof uses `{foreach sections as section}` and `{if section.children}`. The real card-grid uses `{foreach props.items as item}` and `{if item.href}`. Two cards rendered; only the first emitted `<a href="/one">Learn more →</a>`. | **satisfied-by-design** |
| Nested composition recursion | Render child block lists without an infinite include | **supported** | Proof recursively invokes `{include "composition.disyl" sections=section.children}` and observed `<blockquote>“Nested”</blockquote>` from the real quote block in both modes. A generated 25-level tree stopped and logged an error at the 20-level compiled include guard. `tests/disyl_circular_include_test.php` also returned and logged errors for direct, indirect and self recursion (9/9 assertions). | **fix-at-engine-root**, closed by bounded active include stacks which permit finite re-entry |
| Component/slot mechanism | Determine whether existing components can directly serve data-selected theme blocks | **partial** | `tests/disyl_compiled_component_fallback_test.php` rendered `{ikb_section}` and an included `{ikb_badge}` to section/badge HTML in an engine configured for compiled mode (3/3 assertions). Components receive parsed attrs, rendered children, and the current context through `renderComponent(..., $context)`, but names dispatch to registered callbacks/governed components; they do not resolve theme `renderer.template` paths dynamically. Slots belong to that component contract. Dynamic include is the theme-block primitive. | **satisfied-by-design**; do not overload governed components with theme lookup |
| Escaping and safety | Preserve entity-view-equivalent output safety | **supported** | Proof supplied hero title `<Ready>` to the unchanged real hero block (`{props.title | esc_html}`); interpreted and compiled output was `<h1>&lt;Ready&gt;</h1>`. Real block templates contain no `|raw`. No filter or bypass was added. | **satisfied-by-design** |
| Compiled-mode parity | Production compiled rendering must match feasibility behavior | **supported** | The complete proof ran once with compiled mode disabled and once enabled. Every expected hero, nested quote and two-card fragment was present and each run reported no engine errors. `tests/disyl_compiled_component_fallback_test.php` additionally confirmed component fallback while compiled mode remained enabled. | **fix-at-engine-root**, closed by expression-bearing include AST/compiler support |

## Engine contract added

`{include <identifier-or-property-path> [key=expression ...]}` evaluates the include target at render time. Quoted `{include "path" ...}` behavior is unchanged. Targets must resolve to a non-empty string and still pass through the existing template path resolver (including traversal controls). Parameters retain their values, so arrays/maps can be passed whole. Includes maintain a maximum active depth of 20 in interpreted and compiled execution. Finite recursive re-entry is allowed; excessive or accidental recursion is stopped and reported.

This is intentionally not a general output escape hatch. Included templates use the existing expression/filter escaping rules and theme safety policy.
